# Dispatch (GUI session)

This is the operating reference for the dispatcher: the main thread of one ZCode desktop session
running `shipflow` in implementation or end-to-end dispatch mode. Local planning and
publication-only runs stop at their own handoffs rather than entering this loop. Each turn it reads the GitHub snapshot,
applies the dispatch policy (design 8.2), launches at most one bounded run, and waits for that
run's run-settled notification. The reasons are in design 8.1-8.2; the coordinator rules are in
`SKILL.md`.

## Hard limits

- The main thread never mutates GitHub. Every GitHub write happens inside a run, through the
  GitHub kit (`github-kit.dwf.ts`).
- The main thread never reads issue bodies, claim or journal text, PRD text or code. It holds ids,
  counts, paths, exit codes, decision fields and run return values only (z-workflow Pillar 9).
- One active run per project. Never poll: no `TaskOutput`, no loop over `GetWorkflowRun`.
- z-workflow Step 6 (local fast-forward) does not apply. The user's checkout is never written.
- Commands the main thread runs: `snapshot.ts`, `fill-cycle.ts` (fill and `--verify`), the drift
  diffs, `ListWorkflowRuns`, `CreateWorkflow` with `path`, `ResumeWorkflowRun` on stopped runs, and
  the z-workflow skill for bespoke scripts. Nothing else.

Run every command from `<root>`, the absolute project root. Other variables: `<OWNER/NAME>` the
repository, `<builder>` the builder login, `<n>` the PRD issue number (charter
`dispatcher.prd_issue`), `<csv>` comma-separated issue numbers, `<slug>` a per-turn slug of lowercase
letters, digits and hyphens (for example the first issue number plus a UTC time).

## Start-up checklist

Check once per session, before the first turn:

- [ ] Project open in the ZCode desktop app, dynamic workflows enabled, permission mode chosen in
      the app (autonomy rules: Confirmation dialog).
- [ ] `hooks/hooks.json` merged into `<root>/.zcode/config.json`, and the session started after the
      merge. The probe `git push --force origin wf/probe` must be denied and logged.
- [ ] `<root>/autopilot.yaml` generated by setup and on the base branch; `bun` and `git` on the PATH.
- [ ] The INSTALL.md verification table passes for this project.
- [ ] Resolve user intent: `shipflow implement` for existing approved tasks, or `shipflow dispatch`
      only for explicitly authorized composed delivery. Keep the chosen mode on later turns.
      A planning-only or publication-only request does not enter this loop.
- [ ] Claude remote control connected when a person drives the session from elsewhere.

## Per-turn procedure

A turn starts at a run-settled notification, a human message, or session start. Run the steps in
order; a step that ends the turn stops the procedure. Before any snapshot, verify that the
current request authorizes implementation. Session tool permission does not grant that authority.
If the user names individual tasks rather than the queue, dispatch a bespoke scoped run and
stop after those tasks; this queue policy does not widen that selection.

1. **Read the wake-up.** From a run-settled notification take the run id, terminal state and final
   return value. Use ids, counts and outcome; ignore prose. Handle stopped and errored runs first
   (section Stopped and errored runs).
2. **Find an active run.** Call `ListWorkflowRuns` for the project. If a run is still in progress,
   keep its id for step 3.
3. **Snapshot.**

   ```
   bun .zcode/skills/shipflow/scripts/snapshot.ts --repo <root> --gh-repo <OWNER/NAME> --login <builder> --prd-issue <n> --charter <root>/autopilot.yaml --mode <implement|dispatch> [--active-run <id>] [--audit-due]
   ```

   Output is one JSON object `{ snapshot, decision }`. Non-JSON output, or `snapshot.ok` false, ends
   the turn with the error line. `--mode` defaults to `implement`, which never starts kickoff
   or adds a milestone task plan. Optional flags: `--active-run` from step 2; `--audit-due`
   when the owner asks or the agreed audit cadence is reached.

4. **Branch on `decision.action`** using the table below. Pass `decision.issues`, `decision.release`,
   `decision.promote`, `decision.stage` and `decision.milestone` into the launch exactly as given.
5. **Fill the task cycle** (`task-cycles` and `m0-only` only):

   ```
   bun .zcode/skills/shipflow/scripts/fill-cycle.ts --repo <root> --charter <root>/autopilot.yaml --issues <csv> [--release <csv>] [--promote <csv>] --slug <slug> --out <root>/.zcode/workflow-drafts/autopilot-cycle-<slug>.dwf.ts
   ```

   Exit 2 (charter errors) and exit 1 (every issue refused) end the turn; print the refusal lines.
   Otherwise read the one JSON line and keep its `lanes` and `refused` counts.

6. **Verify the draft:**

   ```
   bun .zcode/skills/shipflow/scripts/fill-cycle.ts --verify <root>/.zcode/workflow-drafts/autopilot-cycle-<slug>.dwf.ts
   ```

   Silent exit 0 passes. `ERROR drift line <n>` ends the turn without a launch.

7. **Run the drift checks** (section Drift checks) on the draft. Any output ends the turn without a
   launch.
8. **Launch.** Before the call, state the command set in one line by reference: the template command
   set (task-cycle-spec section 4) plus the charter gate names. Then CreateWorkflow with `path` set
   to the draft and `name` `zflow-autopilot-<slug>`. The confirmation rules apply.
9. **Bespoke runs** (`kickoff`, `fix-main`, `advance`, `decompose`, `unblock`, `audit`, `finish`, and
   the release-only run under Idle): write no script in the main thread. Invoke the z-workflow skill
   with the autopilot brief extension (`references/brief-extension.md`) and the decision as payload:
   `action`, `stage`, `milestone`, `issues`, `release`, `promote`, the charter path and the PRD paths
   in scope. The planner or author writes the script under `.zcode/workflow-drafts/` and returns its
   path. Run the drift checks on that path, then CreateWorkflow with `path`.
10. **End the turn** with one line: `launched run <id>: <action> <issues>`. Do not wait inside the
    turn; the next turn starts at the notification.

## Decision to action

| `decision.action` | Meaning | Turn does | Payload to the run |
|---|---|---|---|
| `busy` | A run is active | End turn: `busy: run <id>` | none |
| `paused` | `autopilot:paused` on the PRD issue | End turn: `paused: <reason>`. Resume after owner direction removes the pause | none |
| `needs-plan` | Implementation-only lacks planning/publication, reaches undecomposed work, or blocked tasks require a planning decision | End turn with the missing scope. Propose planning without starting it | stage, milestone or issue ids |
| `kickoff` | Stage `decision.stage` (S1 to S6) is next. No `kickoff:*` label means S0 | S1 to S6: step 9. S0: end turn with `S0: owner accepts the charter; setup (INSTALL section 3) sets kickoff:S1` | stage, PRD issue, charter path |
| `m0-only` | PRD PR open in `window` mode; only M0 tasks may run | Step 5 with the M0 issues | issues, promote |
| `wait-approval` | `human` mode; PRD PR open | End turn: `waiting for approval of PRD v<n>` | none |
| `fix-main` | Red `main`: open `stop-the-line` issue | Step 9, fix-main brief | issues |
| `advance` | PRs in `state:review` need a rebase or finding fixes | Step 9, advance brief | issues, release |
| `decompose` | End-to-end dispatch only; rolling breakdown: current milestone 70% or more done, next milestone has no tasks | Step 9, decompose brief | milestone, release |
| `task-cycles` | Ready or promotable batch chosen by the policy | Steps 5 to 8 | issues, release, promote |
| `unblock` | Open tasks, none ready, some blocked | Step 9, unblock brief: split, spike or PRD change | issues, release |
| `audit` | Audit due | Step 9, audit brief: L3 to L5 on `main`, parity, retro | release |
| `finish` | Project done check passed | Step 9, finish brief: done check, tag, final report | release |
| `idle` | Nothing to launch | End turn: `idle`. With a non-empty `release`, run the release-only run (section Idle) | release |

The policy fills `release` only from its step 6 on. So `busy`, `paused`, `kickoff`, `wait-approval`,
`m0-only`, `needs-plan` and `fix-main` return an empty `release`. Every launched run releases its `release` issues
first (kit `release` with `bumpAttempt: true` and `to: "ready"`); the task-cycle template does this
in its Release and promote phase.

## Drift checks

Run both before every launch, from `<root>`, against the draft the launch will use (for a bespoke
run, the path the author returned). Both must print nothing.

```
KIT="<root>/.zcode/skills/z-workflow/persona-kit.dwf.ts"
[ -f "$KIT" ] || KIT="$HOME/.zcode/skills/z-workflow/persona-kit.dwf.ts"
DRAFT="<root>/.zcode/workflow-drafts/autopilot-cycle-<slug>.dwf.ts"
diff <(sed -n '/^\/\/ persona-kit:start/,/^\/\/ persona-kit:end/p' "$KIT") <(sed -n '/^\/\/ persona-kit:start/,/^\/\/ persona-kit:end/p' "$DRAFT")
diff <(sed -n '/^\/\/ github-kit:start/,/^\/\/ github-kit:end/p' "<root>/.zcode/skills/shipflow/github-kit.dwf.ts") <(sed -n '/^\/\/ github-kit:start/,/^\/\/ github-kit:end/p' "$DRAFT")
```

The first diff is z-workflow's persona-kit check (`SKILL.md`, Specialist agents in workflows). The
second proves the draft's GitHub kit block matches the installed kit. Task-cycle drafts carry both
blocks, so both diffs run for them; a bespoke draft runs each diff only when it carries that block.
Any output ends the turn. A changed kit is fixed in its source through a skill PR, never by editing
a draft.

## Chaining on run-settled notifications

- A run's completion notification arrives on its own with the final return value and the reported
  items. It is the wake-up: the session takes the next turn with no user message and runs step 1.
  Spike S1 confirms this chain. Until S1 passes, a person or remote control sends the wake-up if the
  chain stops.
- Exactly one run is in flight. The launching turn ends at step 10, so no second launch happens
  before the notification.
- A kickoff stage hands over only when its run calls `setKickoffStage` on success. The next snapshot
  then reports the next stage and the policy launches it. A failed or stopped stage leaves the
  label where it was.
- Return values are compact by contract: the autopilot brief extension asks for ids, counts, exit
  codes and kit outcomes, never issue or PRD text. A return value with prose is a finding for the
  skill owner, not an input to the next decision.

## Idle

- `idle`, `wait-approval`, `paused` and `busy` end the turn with one status line. No timer wakes
  the session; spike S1 decides whether one exists. Until then a nudge through Claude remote control,
  or the next human message, starts a turn at step 1.
- The GitHub Actions watchdog (`templates/watchdog.yml`) only opens a `kind:bug` issue titled
  `autopilot stalled`. It never launches a run; a person reads that issue and nudges the session.
- `idle` with a non-empty `release` (stale claims) needs a run, because the policy attaches `release`
  only to launched runs and nothing else would clear the claims. Launch a release-only run through
  step 9: for each issue in `release`, call the kit's `release` with `bumpAttempt: true` and
  `to: "ready"`, using the nonce from the kit's claim records. The run returns the counts.

## Context rules

- The main thread holds run ids, decision fields, the fill-cycle JSON line, run return values and
  status lines. Nothing else: no issue bodies, PRD text, code or gate logs.
- Start a fresh session when `decision.milestone` moves past the milestone of the last launched run,
  after 30 launching turns in one session, or when the app's context indicator passes about 60%. End
  the turn with `restart: <reason>`. The owner or remote control opens a new session in the project
  and runs `shipflow dispatch`. Nothing is lost: the first turn rebuilds all state from GitHub.
- Context growth per dispatch is measured in spike S1. The 30-turn and 60% figures hold until then.

## Confirmation and product review

Owner decision D16 (design 0.1, 2026-10-18): allowing workflow creation once for the session
suppresses later workflow dialogs in that session. Reuse that grant within the authorized
phases and charter. Do not stop merely because the owner selected session-wide permission.
A new session or changed permission scope can require another allowance.

Continue to inspect each run's command set and run drift checks before launch. This review
is independent of whether ZCode displays a dialog. Human PRD approval, publication authority
and per-cycle product review remain separate from permission to call `CreateWorkflow`.
A user who requested a local plan still gets a local plan, even with session-wide permission.

The owner also proposed AXTree-assisted confirmation. It is an optional fallback, not an
implemented or verified helper. If added later, it may activate the confirmation only for the
expected ZCode session and an already-authorized workflow whose command set matches the
requested scope. Unexpected dialogs or expanded permissions return to the owner. An automated
click cannot count as human approval of a PRD or an unrequested phase. Session-wide permission
is the normal path and needs no per-run UI script.

Supervised mode can retain per-cycle product review when the user chooses it. That is a
workflow policy, not a claim that ZCode always requires another confirmation.

## Stopped and errored runs

| Terminal state | Dispatcher does |
|---|---|
| completed | Normal turn from step 1 |
| errored (script threw, overran a cap, lost an artifact) | No resume: `ResumeWorkflowRun` refuses errored runs, and the dispatcher does not amend. End turn: `errored: run <id>, script <path>`. The owner or the z-workflow author fixes the script and resubmits it with `AmendWorkflow` and `path` |
| stopped, `interrupted` (owning process exited) | `ResumeWorkflowRun` once |
| stopped, `provider` (sign-in expired, quota) | The owner clears the fault named in `<error>`, then `ResumeWorkflowRun` once |
| stopped, `user` | Leave it. End turn with the status line unless the owner asks to resume |
| stopped, `model` | Do not resume. End turn with the status line |
| superseded | No notification. Nothing to do |
| "waiting for provider" badge | Nothing. Provider retries are not failures; the one stall notification after twenty minutes needs nothing either |

A resumed run that stops or errors again is not resumed a second time. Its issues keep their claims
until the claim TTL passes; the next launched run that carries them in `release` returns them to
ready with attempt plus one (design 9).

## Unknowns settled by spike S1 (design 8.1)

Run S1 on a scratch repo, driven through Claude remote control. Until it is recorded, the rules above
describe the intended behavior; the once-per-session behavior is owner-reported.

1. Verify the owner-reported session grant: allow workflow creation once, then launch a second
   run without a dialog. Record app version, permission mode and hook observations. Repeat in a
   new session to check when permission resets. This revision does not claim a live GUI test.
2. Whether the session wakes on the run-settled notification and launches the next run with no user
   turn.
3. Whether anything wakes an idle session on a timer. If not, nudges stay manual.
4. Whether a stopped run resumes with `ResumeWorkflowRun` after the app restarts.
5. How fast main-thread context grows per dispatch, which sets the restart thresholds.
